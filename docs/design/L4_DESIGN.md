## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 协议版本 | OUCH **4.2**：每种消息定长，没有 5.0 的可选附加字段（appendage），子集好界定、逐字节测试好写。5.0 的差别写进 §1.5，留作扩展。 |
| 分层 | SoupBinTCP 负责"可靠、有序地把服务端消息送到客户端"（登录、会话、隐式序号、断线后重放、心跳、登出 / 会话结束）；OUCH 负责订单语义。两层**互不知道对方的内容**。 |
| 客户端为什么不需要入站序号 | OUCH 的入站消息全部**可以安全重发**（重复令牌被忽略、撤单写的是"目标剩余量"），所以入站不需要可靠投递。这是整个恢复设计的支点（§2.3）。 |
| 撮合 | 服务端 = SoupBinTCP + OUCH + 自己的一份行情订单簿（`FeedHandler`）+ 现有 `SimExchange`（内部是 L1 `MatchingEngine`）。成交的产生方式与进程内模式完全相同。 |
| 可验证性 | **锁步模式**：每个行情事件、每个请求都等到"静默"（服务端回报已全部到达）再继续，订单 / 成交 / 持仓哈希必须与进程内 `TradingStage` **逐位相同**。**自由运行模式**：只检查不变量，同时记录两端实际看到的交错顺序，离线按记录重放必须重现两端的摘要（§4）。 |
| tick-to-trade | 起点：ITCH 帧开始解码；终点：OUCH 字节交给内核（`send()` 返回）。进程内与回环网络**分开报告**，回环再加"线到交易所"和"tick-to-ack"两段。都只是同一台机器上的软件路径，不能与业界线到线（wire-to-wire）数字比较（§3）。 |

## 1. 协议：OUCH 4.2 子集

### 1.1 数据类型（规范 §1.2）

- 整数：无符号大端。
- Alpha：左对齐、右补空格。
- 令牌（Order Token）：14 字节，字母数字和空格，**区分大小写**，**同一 OUCH 账户内当日唯一**。
- 价格：整数，6 位整数 + 4 位小数（与 ITCH 5.0 相同的 1e-4 美元，`uint32` 直接沿用）。最大价格 $199,999.9900（`0x7735939C`）；
  `0x7FFFFFFF` 和 $200,000.0000 被当作市价单 → **本子集拒绝**（只做限价单）。
- Time in Force：秒数；特殊值 0 = IOC，99998 = Market Hours，99999 = System Hours，99996 = Extended Trading Close；> 99,999 非法。
- 时间戳（出站）：8 字节，午夜起的纳秒数。

### 1.2 入站消息（客户端 → 交易所，**不编序号**，规范 §2）

| 类型 | 消息 | 长度 | 字段（偏移:长度） |
|---|---|---|---|
| `O` | Enter Order | **49** | Token 1:14 · Buy/Sell 15:1（B/S/T/E）· Shares 16:4（0 < x < 1,000,000）· Stock 20:8 · Price 28:4 · TIF 32:4 · Firm 36:4 · Display 40:1 · Capacity 41:1 · ISO 42:1 · MinQty 43:4 · Cross Type 47:1 · Customer Type 48:1 |
| `U` | Replace Order | **47** | Existing Token 1:14 · Replacement Token 15:14 · Shares 29:4 · Price 33:4 · TIF 37:4 · Display 41:1 · ISO 42:1 · MinQty 43:4 |
| `X` | Cancel Order | **19** | Token 1:14 · Shares 15:4 |

语义上最容易写错的三点，实现和测试都要逐条覆盖：

1. **Cancel 的 Shares 是"撤单后的目标订单量"（intended order size），不是减量**；0 = 全撤。
   所以同一条撤单重发两次结果不变（幂等），"撤单太晚"也不需要专门的回报：此时成交回报已经在路上（规范 §2.3）。
2. **Replace 的 Shares 是整条改单链的总责任量，包含此前已成交的部分**（规范 §2.2 的 500 / 100 / 400 例子）；
   而 Replaced 回报里的 Shares 是"改单完成后还挂着的量"。改单总是丢失时间优先级。
3. Replace 的四种结局（规范 §2.2）：原令牌已不在 / 新令牌用过 → **静默忽略**；原单在但改单参数非法 → **Canceled 把原单撤掉**，
   新令牌未被消耗；原单在但不能撤（集合竞价晚期）→ **Rejected**，原单不变，新令牌被消耗；成功 → **Replaced**。

子集只实现上述字段的校验与回显，不实现 Display / Capacity / ISO / MinQty / Cross Type 的业务含义：
服务端只接受 Display=`A`/`Y`、MinQty=0、Cross Type=`N`、TIF ∈ {0, 99998, 99999} **【本项目约定】**，其余取值回 `Rejected`
（原因码按规范表选最接近的：价格 → `X`，股票 → `S`，其他 → `O`）。

### 1.3 出站消息（交易所 → 客户端，**全部编序号**，规范 §3）

| 类型 | 消息 | 长度 | 关键字段 |
|---|---|---|---|
| `S` | System Event | **10** | Timestamp 1:8 · Event Code 9:1（`S` 开始 / `E` 结束） |
| `A` | Accepted | **66** | Timestamp · Token 9:14 · B/S 23 · Shares 24:4 · Stock 28:8 · Price 36:4 · TIF 40:4 · Firm 44:4 · Display 48 · **Order Reference Number 49:8** · Capacity 57 · ISO 58 · MinQty 59:4 · Cross Type 63 · **Order State 64**（`L` 存活 / `D` 已死）· BBO Weight 65 |
| `U` | Replaced | **80** | Timestamp · Replacement Token 9:14 · B/S 23 · **Shares 24:4（剩余挂单量）** · Stock 28:8 · Price 36:4 · TIF 40:4 · Firm 44:4 · Display 48 · Ref Number 49:8 · Capacity 57 · ISO 58 · MinQty 59:4 · Cross Type 63 · Order State 64 · **Previous Token 65:14** · BBO Weight 79 |
| `C` | Canceled | **28** | Timestamp · Token 9:14 · **Decrement Shares 23:4（增量，不是累计）** · Reason 27:1 |
| `E` | Executed | **40** | Timestamp · Token 9:14 · Executed Shares 23:4（增量）· Execution Price 27:4 · Liquidity Flag 31:1 · Match Number 32:8 |
| `J` | Rejected | **24** | Timestamp · Token 9:14 · Reason 23:1（该令牌不可再用） |

规范要求客户端"预期原因码会增加、支持全部大写字母"——解码器对 Canceled / Rejected 的原因码**只校验是字母**，不做白名单；
未知 Liquidity Flag 同样只做字符集校验。子集外的出站类型（`B` Broken Trade、`G`、`D` AIQ、`P`、`I`、`T`、`M`）解码为
`Skipped`（长度未知时整包跳过——SoupBinTCP 的包长已经给出边界，这是 OUCH 定长 + Soup 分帧的好处）。

### 1.4 编解码器设计（沿用 ITCH 解码器的约定，D-047）

- 零拷贝视图解码：`decode(span) -> {status, Message}`，`status ∈ {Decoded, Skipped, Empty, UnknownType, BadLength, InvalidField}`。
  每种类型**长度必须精确等于规范值**；字段非法（方向不在 B/S/T/E、Shares 越界、令牌含非字母数字空格字符、价格越界、原因码非字母）→ `InvalidField`。
- 编码：写进调用方给的定长缓冲区，不分配；`encode(decode(x)) == x` 对每个合法样本逐字节成立。
- 令牌类型 `Token = std::array<char,14>`，生成与比较都不经过字符串。

测试（L4.1）：每种消息一份**手写十六进制样本**（按规范偏移逐字段写出，注释标偏移）；往返；**逐字节截断**（长度 0 … n−1 全部 `BadLength`）；
逐字段非法值；固定种子变异 fuzz（与 `scripts/fuzz_itch.sh` 相同结构）+ libFuzzer 入口（clang 可用时）：任何输入不崩溃，
`Decoded` 的输入重新编码必须逐字节相等。

### 1.5 为什么不是 OUCH 5.0

5.0 把订单号改为 `UserRefNum`（4 字节整数，客户端单调递增，而不是 14 字节令牌），并引入变长的可选附加字段（TagValue appendage）。
子集若用 5.0，就要实现附加字段的解析与长度校验，测试面翻倍而对本项目要说明的问题（会话、恢复、映射、时延）没有增量。
记录为扩展项：迁移时只换编解码层，网关的订单状态机不变（令牌 → UserRefNum 只是键的类型变化）。

## 2. 会话层：SoupBinTCP 3.00 与真实系统中的处理

### 2.1 SoupBinTCP 的职责（与 OUCH 严格分开）

逻辑包：2 字节大端长度（**不含长度字段本身、含 1 字节类型**）+ 类型 + 负载。逻辑包与 TCP 段没有对应关系（会被拆开或合并）。

| 方向 | 类型 | 包 | 负载 |
|---|---|---|---|
| 双向 | `+` | Debug | 文本，接收方忽略 |
| 服务端 | `A` | Login Accepted | Session 10（**左补空格**）· Sequence Number 20（ASCII，**左补空格**，= 下一条将发送的序号） |
| 服务端 | `J` | Login Rejected | 原因 1：`A` 未授权 / `S` 会话不可用；发完即关闭连接 |
| 服务端 | `S` | Sequenced Data | 一条上层（OUCH 出站）消息 |
| 服务端 | `H` | Server Heartbeat | — |
| 服务端 | `Z` | End of Session | — 之后连接关闭，该会话不能再登录 |
| 客户端 | `L` | Login Request | Username 6 · Password 10（右补空格、不区分大小写）· Requested Session 10（全空格 = 当前会话）· Requested Sequence Number 20（ASCII；0 = 从最新一条开始） |
| 客户端 | `U` | Unsequenced Data | 一条上层（OUCH 入站）消息 |
| 客户端 | `R` | Client Heartbeat | — |
| 客户端 | `O` | Logout Request | — 服务端立即关闭连接 |

- **序号是隐式的**：Sequenced Data 不带序号，双方各自计数；每个会话第一条是 1；Login Accepted 给出本次连接第一条的序号。
- 断线恢复：客户端用"当前会话 + 下一条期望序号"重新登录，服务端从该序号开始**重放**，客户端因此不丢、不乱序地收到每一条出站消息。
- 心跳：任一方超过 **1 秒**没发任何东西就发心跳；服务端约 **15 秒**收不到任何东西就关连接；登录请求须在连接后合理时间内到达（规范举例 **30 秒**）。

**OUCH 的职责**：订单的进入 / 改 / 撤与回报语义、令牌、订单参考号、成交号。OUCH 不知道连接、序号、心跳。

### 2.2 两端各自维护的状态

**服务端（每个逻辑会话 = 每个 OUCH 账户 / 每天，跨连接存在）**
- 会话 ID（10 字节，【本项目约定】`D` + ITCH 文件日期 + 序号，如 `D201901300`）、下一出站序号、**出站消息日志**（重放用，容量预留；
  超出容量 → 发 `Z` 结束会话，计数并告警，绝不在热路径重新分配【本项目约定】）。
- 令牌表：令牌 → 内部订单（状态、剩余量、已成交量、改单链）；**已用令牌集合**（含被拒、被改掉的令牌，当日不可复用）。
- 账户级：当前连接（至多一个）、断线撤单开关、限流令牌桶、持仓（只用于验证）。

**服务端（每个连接，短生命周期）**：`AwaitLogin → LoggedIn → Closed`，接收缓冲（半包拼接）、发送缓冲（`EAGAIN` 时挂起，等 `EPOLLOUT`）、最后收 / 发时间。

**客户端**
- 会话：会话 ID（首次登录后从 Login Accepted 学到）、**下一期望序号**（每收一条 Sequenced Data 加 1）、最后发送时间（心跳）、最后接收时间（超时）、连接状态机（§2.5）。
- 订单：令牌生成器、映射表、每单状态机（§2.3）、待确认的入站请求（重连后重发用）。

### 2.3 订单号映射、重复报单防护与订单状态机

**三种编号**

| 编号 | 谁分配 | 生命周期 | 用途 |
|---|---|---|---|
| `client_id`（u64） | 策略 / OMS | 进程内 | 策略与风控、成交回报对账（现有 `OrderRequest::client_id`） |
| Order Token（14 字节） | **客户端网关** | 当日、账户内唯一；**改单产生新令牌** | OUCH 线上唯一的订单标识 |
| Order Reference Number（u64） | 交易所，Accepted / Replaced 回报 | 当日唯一 | 交易所内部；真实 Nasdaq 中可见订单的参考号与 ITCH Add Order 的参考号一致，可用来在公共行情里找到"自己的单"，精确知道排队位置（真实系统的常见做法；本项目记录为保守成交模型的改进方向，L4 不实现） |

网关维护 `token → order`、`client_id → order` 两张定长开放寻址表（容量在构造时预留，热路径不分配）；
改单成功时把 `order` 从旧令牌**重新挂到**新令牌，旧令牌留在"已用"集合里。改单在途时旧令牌仍可能收到 Executed（规范 §3.4 第二个例子），
所以旧令牌在收到 Replaced 之前**一直有效**。

**令牌生成（重复报单防护的第一层）**：`[会话日期 4][进程启动序号 2][单调计数 8]`，base-36，恰好 14 字节【本项目约定】。
进程启动序号写在本地状态文件里，每次启动加一 → 客户端崩溃重启后也不会复用当天的令牌。真实系统做法相同：令牌必须在
重启后仍唯一，通常由持久化的计数器或"日期 + 进程实例 + 序列"保证。

**交易所侧（第二层）**：重复令牌的 Enter Order **被忽略**（规范 §2.1），重复的改单新令牌被忽略（§2.2），多余的撤单被忽略（§2.3）。
因此**所有入站消息都可以安全重发**——这正是 SoupBinTCP 只保证出站、不保证入站的原因（OUCH §1.1、§2）。

**断线后的恢复流程（第三层，客户端）**
1. 用旧会话 ID + 下一期望序号重新登录；服务端重放断线期间的所有出站消息，网关逐条应用（与正常接收走同一路径）。
2. 重放到达的同时，**把所有仍处于 Pending 状态的请求原样重发**（同一个令牌 / 同一个目标剩余量）：已经到过交易所的会被忽略，
   没到过的这次生效。客户端不需要知道"重放何时结束"——SoupBinTCP 的 Login Accepted 只给起始序号，不给高水位——幂等性让这个问题消失。
3. 新单的重发不会造成重复（同一令牌第二次被忽略），但会造成**过时**：断线可能持续数秒，那笔单是按断线前的行情决定的。
   因此【本项目约定】默认**只重发撤单 / 改单，不重发新单**：Pending 的新单标记 `in_doubt`，等重放里的 Accepted / Rejected 定论。
   "重放何时结束"用规范本身给出的信号判断：服务端只在**超过 1 秒没有发送任何东西**时才发心跳，所以登录后收到的第一个 Server Heartbeat
   意味着重放已经发完；此时仍无定论的新单必然没有到达过交易所（旧连接已关闭，不会再有它的消息被处理）→ 令牌作废，向策略报告拒绝。
   若断线期间交易所执行了断线撤单（§2.4），重放里就有对应的 Canceled，重发的撤单被忽略——结果一致。
   可选的规范式行为（配置开关）：新单也原样重发，换取更快定论、接受过时风险。

**客户端每单状态机**（每个转换都有具名测试）

```
            Accepted(L)                 Executed(全部)
PendingNew ───────────▶ Live ────────────────────────▶ Filled
   │  │ Accepted(D)      │ ▲ Executed(部分) → 仍 Live（leaves 减少）
   │  └──────────────▶ Dead
   │ Rejected          │ 发撤单          Canceled(leaves→0)
   └──────────▶ Rejected ├──────▶ PendingCancel ─────────────▶ Canceled
                       │          │ Executed → 仍 PendingCancel（成交与撤单赛跑）
                       │ 发改单    │ Canceled(部分减量) → 回 Live
                       └──────▶ PendingReplace ── Replaced ──▶ Live(新令牌)
                                  │ Canceled(原单被撤：改单参数非法) → Canceled
                                  │ Rejected(改单被拒) → Live(原单不变)
断线：所有非终态 → 保留原状态并标记 `in_doubt`，重放 + 重发后解除（§2.3 第 3 条）
```

非法转换（例如 Filled 之后又来 Executed、未知令牌的回报、成交量超过剩余量）→ 计数 + 告警 + 触发风控熔断（`TripReason::GatewayInconsistent`，新增）。
这是"不超仓"的最后防线：网关对自己的持仓认知与交易所回报不一致时，停止交易而不是猜。

### 2.4 断线撤单与交易所侧限流

**断线撤单（Cancel-on-Disconnect）**：真实交易所普遍把它作为**端口级配置**提供（OUCH / SoupBinTCP 规范本身不定义它；
交易所另有风控门户的"一键撤单"/kill switch）。本项目服务端按账户开关：连接断开（对端关闭、15 s 无接收、协议错误）时，
撤掉该账户所有存活订单，每笔生成一条 **Canceled，原因 `Z`（System cancel）**【本项目约定：规范未规定断线撤单用哪个原因码】，
照常编入会话序号——客户端重连时在重放里看到它们，持仓认知保持一致。登出（`O`）是否触发同样可配置（默认触发）。

**交易所侧限流**：OUCH 4.2 的拒单原因表里有 `x` Port Message Rate Restriction、`w` Symbol Message Rate Restriction、
`y` Duplicate Message Rate Restriction——即真实 Nasdaq 对超速的**新单 / 改单回 Rejected**。服务端实现：每账户令牌桶（速率、突发可配），
超限的 Enter / Replace 回 `Rejected 'x'`，**撤单不限流**【本项目约定，与 L3' 风控"撤单永不拦截"一致：限流的目的是保护交易所，
挡住撤单只会让风险敞口更大】。另外接收侧有**读取预算**：每个连接每轮事件循环最多处理 N 条消息，剩余留在内核缓冲区——
这是 TCP 反压，慢不会变成丢；对端写满后自然被阻塞。

客户端风控的 `RateLimit` 仍是第一道；服务端限流是纵深防御，测试用一个绕过风控的原始客户端打满它。

### 2.5 会话状态机（sans-IO，D-059 拟定）

会话层写成**不碰 socket 的纯状态机**：输入 = 收到的字节 + 当前时间（注入的时钟），输出 = 要发的字节 + 上层事件 + 下一个超时点。
epoll 驱动层只做"读 → 喂给状态机 → 写出它产生的字节"。好处：每个转换都能用手写字节和假时钟测试，不需要网络、不需要 sleep，
在 TSan 下也确定。

**客户端**
```
Disconnected ─connect()─▶ Connecting ─connected─▶ LoginSent ─'A'─▶ LoggedIn ─logout()─▶ LogoutSent ─close─▶ Disconnected
                              │ 失败                │ 'J' → Rejected（终态，不自动重试）     │ 'Z' → SessionEnded（终态）
                              ▼                     │ 超时 / 断开                            │ 15 s 无接收 / 断开 / 协议错误
                         Disconnected ◀─────────────┴────────────────────────────────────────┘ （可重连，保留会话与序号）
```
LoggedIn 内：每收一条 `S` → 期望序号 + 1 并交给上层；`H` 只更新接收时间；`+` 忽略；空闲 1 s → 发 `R`。
（实现补记，L4.2：Login Accepted 的序号或会话与请求不符 → 终态 `Failed`（`SequenceMismatch`），不自动重连；
发送缓冲容量固定，满时 `send()` 返回 false 由上层保留消息；服务端出站消息从会话日志按缓冲余量**拉取**，客户端 15 s 不读 → `SlowConsumer` 关闭。）

**服务端（每连接）**
```
AwaitLogin ─'L' 合法─▶ LoggedIn ─'O' / 断开 / 15 s 无接收 / 协议错误─▶ Closed（→ 账户断线撤单）
    │ 'L' 非法 → 发 'J' → Closed      │ 会话结束 → 发 'Z' → Closed
    │ 30 s 无登录 / 首包不是 'L' → Closed
```
登录校验：用户名口令（不区分大小写）；会话 ID 全空格或等于当前会话；请求序号 0 = 从最新开始，1…下一序号 = 从该处重放；
**请求序号大于服务端下一序号 → 接受并从服务端的下一序号开始，Login Accepted 如实给出该序号**【本项目约定：规范 2014 修订提到此情形但正文未给出处理】，
客户端发现"服务端给的序号小于我期望的"时视为状态不一致（告警 + 熔断），因为这只可能是连错了会话或服务端丢了状态。
同一账户已有连接时的新登录：~~拒绝 `J 'S'`~~ → 实现时改为**接管**：新连接登录成功后关闭旧连接（先执行断线撤单，撤单消息进入会话日志，新连接的重放里就有）【本项目约定，L4.3：客户端重连时服务端可能还没察觉旧连接断开，拒绝会让客户端进入终态 `Rejected`】。

**分帧的错误处理**：长度 0（必须至少含类型字节）、长度超过上限（【本项目约定】最大逻辑包 1 + 80 + 余量 = 256 字节；Debug 包可更长，
单独上限 4 KiB）、客户端发来服务端类型（或反之）→ 协议错误 → 关闭连接。测试：任意字节流在**每一个字节边界**拆分 / 合并后，
解析结果与一次性喂入相同。

### 2.6 模拟交易所服务端（单线程 epoll）

```
         TCP (OUCH over SoupBinTCP)                 控制通道（同进程，SPSC + eventfd）
 客户端 ─────────────────────────────▶ epoll 事件循环 ◀───────────── 行情：第 i 条输入的第 k 个事件 / 屏障
                                        │
     会话状态机（每连接） → OUCH 解码 → 账户 / 令牌表 → 限流 → SimExchange.submit(…, 自己的行情订单簿)
                                        │                                 └─ L1 MatchingEngine（未改动）
     行情事件 → 自己的 FeedHandler → SimExchange.on_market → 成交 → Executed（编序号，写入会话日志）
```

- **交易所自己维护一份行情订单簿**：服务端与客户端各跑一个 `FeedHandler`，喂同一份 ITCH 输入。保守成交模型下单时要读"此刻我方价位的排队量"，
  这必须是交易所看到的订单簿，而不是客户端发来的。
- 行情从控制通道进入（L4 的行情仍来自文件；L5 换成组播）。控制消息是**按事件**的（第 i 条输入、第 k 个 BookUpdate），
  服务端在第一次用到第 i 条输入时把它喂给自己的 `FeedHandler`——这样服务端处理行情的粒度与进程内 `TradingStage` 一致（§4.1）。
- 改单：`MatchingEngine` 只有新单 / 撤单，Replace = 撤原单 + 以新令牌下新单（排到队尾），这与规范"改单总是丢失时间优先级"一致；
  Replaced 的 Shares = 总责任量 − 已成交量（不足 0 → 按规范第 2 种结局撤原单）。
- 事件循环：水平触发；非阻塞 socket；`TCP_NODELAY`；超时由 `epoll_wait` 的等待时长 = 最近截止时间实现（不另用 timerfd）；
  每轮：处理控制通道 → 处理就绪连接（受读取预算约束）→ 处理到期的心跳 / 超时 → 刷发送缓冲。
- 接受连接、建会话日志属于冷路径，允许分配；处理消息的热路径不分配（沿用 L3' 的零分配守卫测试）。
- **日志（journal）**：服务端把"实际处理顺序"记成定长记录（`{行情 i,k}` 或 `{入站 账户, 消息字节}` 或 `{断开 账户}`），见 §4.2。

## 3. tick-to-trade：定义，以及进程内 / 回环网络各能说明什么

### 3.1 定义

本项目的 **tick-to-trade = 从 ITCH 帧开始解码（t0）到对应 OUCH 入站消息的字节交给内核（`send()` 返回，t_send）**，
只统计**产生了订单的行情事件**（不是 1/N 采样——不产生订单的事件不是 tick-to-trade 的样本）。
一个行情事件触发多笔订单时，每笔各算一个样本，并单独报告"第一笔"。

在 L3' 延迟瀑布（decode → queue → book → strategy → risk → engine）的基础上拆成：

| 段 | 起止 | 模式 |
|---|---|---|
| T1 tick-to-decision | t0 → 风控放行 | 进程内（现有瀑布的前缀） |
| T2 tick-to-encoded | t0 → OUCH + Soup 字节写进发送缓冲 | 进程内（网关接"空传输"，不发 syscall） |
| T3 **tick-to-trade** | t0 → `send()` 返回 | 回环 TCP |
| T4 wire-to-exchange | 客户端 `send()` 前 → 服务端完成解码该消息 | 回环 TCP（同机同一 TSC，跨线程可比） |
| T5 tick-to-ack | t0 → 客户端解码出对应 Accepted | 回环 TCP，含交易所处理与回程 |

单线程与流水线（解码线程 → SPSC → 订单簿线程）两种模式都报告；分位数 p50 / p99 / p99.9，**扣除计时开销**（沿用 BENCHMARK 的方法：
测 `rdtsc` 对的空测量中位数并减去），并给出样本数。每个数字附**测量环境**（CPU 型号、核数、内核、虚拟化、是否绑核、编译器与选项）；
云端容器里测得的一律标"云端 VM，待本机复测"并给出复测命令。

### 3.2 进程内能说明什么、不能说明什么

**能**：关键路径上**软件本身**的成本——解码、订单簿更新、策略、风控、编码各自多少，哪一段主导；同一份输入可重复、可对比（还能配合 cachegrind
指令数门槛做回归）；不同实现（CRTP / 虚函数、单线程 / 流水线）之间的相对差异。
**不能**：任何 I/O 的成本。T2 不含 syscall、内核协议栈、网卡、线路和交易所——它是下界，不是"我们的系统多快"。

### 3.3 回环网络能说明什么、不能说明什么

**能**：在 T2 上增加的 `send()` 系统调用、内核 TCP 协议栈（两遍）、服务端被 epoll 唤醒的调度延迟、交易所侧处理；T5 给出完整的请求 / 应答回路。
它暴露的是"把一个用户态程序接上内核 socket"的真实代价和尾部（唤醒、抢占、软中断），通常比 T2 大一到两个数量级。
**不能**：
- 网卡、线缆、交换机、真实交易所网关——回环不经过 NIC（没有中断合并、DMA、PHY），不是线上时延；
- 内核旁路（Onload / DPDK / ef_vi）或 FPGA 的效果——生产低延迟系统通常不用内核 TCP 栈；
- 跨机时钟：真实的线到线测量在交换机镜像口 / 网络分光上用硬件时间戳，两端需要 PTP 同步；同机同 TSC 回避了这个问题，也就测不到它；
- 云端 VM 的噪声（vCPU 抢占、无法 isolcpus）会放大尾部：p99.9 在这里主要反映宿主机调度，不反映代码。

所以对外的表述只能是："同一台机器、内核回环 TCP、未做内核旁路时，软件路径的 tick-to-trade 分布是 X"——不与业界宣传的线到线数字比较。

## 4. 网络模式下回报时机不确定时如何保留可验证性

问题：进程内 `TradingStage` 是同步的——下单后回报立刻回来、在下一个行情事件之前送达策略，所以订单 / 成交 / 持仓哈希是输入的纯函数（L3' 的
"回放 == 流水线"门槛）。接上 TCP 之后，回报何时到达取决于两端的调度，同一份输入可能产生不同的交错，从而不同的策略行为。
对策是两种模式，各管一件事：

### 4.1 锁步模式：证明"网络栈是透明的"

把交易所当成 `TradingStage` 的一个**可替换的 Exchange 实现**：`TradingStage<S, Ex = SimExchange>`。默认参数下代码与今天逐字相同
（指令数门槛验证零开销）；锁步模式用 `GatewayExchange`，它的 `submit` / `on_market` 在返回前一直等到**静默**：

- **静默的定义**：客户端每发一条消息（行情事件走控制通道，订单走 TCP），服务端处理完后在控制通道回一个**屏障应答 `{已处理的第 n 条, 当前出站序号 K}`**；
  客户端从 TCP 读到序号 K 为止，收到的回报即为这一步的全部回报。为什么需要屏障：多余的撤单、已不在的改单按规范**不回任何消息**，
  "等下一条回报"会永远等下去；出站序号是唯一可靠的水位线。
- **嵌套顺序与进程内一致**：进程内，一个行情事件产生的成交批次（fill1、fill2）先全部算出，再逐条交给策略；策略对 fill1 的反应（新请求 R）
  在 fill2 送达之前就提交并拿到回报。锁步下 `on_market` 先把整批（到水位线 K）读进本地队列，再逐条交付；R 的回报序号 > K，
  由 R 自己的 `submit` 收取——交付顺序与进程内逐条相同。
- **撤全部的顺序**：`TradingStage` 在不可交易 / 熔断时"撤掉所有挂单"，今天按 `SimExchange` 的槽位顺序遍历。网关看到的槽位顺序不一定相同，
  因此把顺序**规范化为 `client_id` 升序**（两种 Exchange 都按此遍历）。这会改变 L3' 已记录的少量交易哈希（同时撤多笔时）——属于 L3' 代码，
  不是 L1；改动前后的哈希与原因写进 DECISIONS 并重新记录【需要确认，见 §6】。
- **门槛**：同一份输入（合成样本 + 固定种子的多份随机流，两种成交模型，单线程与流水线），锁步网络模式的订单 / 成交 / 持仓哈希与进程内**逐位相同**。
  锁步模式下服务端时钟用 ITCH 时间，限流按需关闭或用确定性时钟，心跳不编序号、不进入哈希。

锁步证明的是：编解码、会话层、令牌映射、状态机、服务端的订单处理，在"没有时序竞争"时没有丢、多、改任何一条信息。
它**不**证明系统在竞争下的行为——那是 4.2 的事。

### 4.2 自由运行模式：不变量 + 记录 / 重放

客户端全速消费行情、发单不等待；回报到达时（订单簿线程在每个行情事件前非阻塞地取出已到达的回报）交给策略；服务端从控制通道
非阻塞地取行情，与 TCP 入站在 epoll 循环里自然交错。结果不确定，所以不比哈希，只检查**不变量**（运行中持续检查，结束时再对账）：

1. **不超仓**：任意时刻，客户端认知的 `|持仓| + 同方向挂单量 ≤ max_position`；服务端按回报算出的持仓也不超过（服务端知道风控配置，只用于验证）。
2. **无重复订单**：服务端收到的每个令牌至多建立一个订单；客户端生成的令牌全局唯一（含重启）；一个 `client_id` 至多对应一条存活链。
3. **状态机合法**：客户端每单的每个转换都在 §2.3 的图里；服务端没有对已死订单产生成交。
4. **排空后对账**：输入结束后客户端停止下新单、撤掉全部、等到静默；此时两端的每单终态、成交总量、持仓、现金逐项相等，
   序号无缺口（客户端收到 1…K，K = 服务端最后序号）。
5. 故障注入（断线、重连、限流）下 1–4 仍然成立；断线撤单后两端都没有存活订单。

**记录 / 重放**：不确定性只来自"两端看到的交错顺序"。两端各记一份定长日志——服务端记"处理顺序"（§2.6），客户端记"每个行情事件之前交付了哪些回报序号"。
两端的业务逻辑（`OuchServer` 核心与 `TradingStage` + 网关）都是 sans-IO 的纯函数，**离线按日志重放必须重现两端的出站流哈希与订单 / 成交 / 持仓哈希**。
这样一次不确定的运行也能被逐位复现、定位：出了问题，把日志带回来就能单步调试。日志是定长记录、预留容量，写满就停止记录并标记（不影响运行）。

3. **断线后默认不重发新单**（重发不会重复，但单子已按过时行情决定；用"登录后第一个服务端心跳 = 重放结束"判定未到达的新单）——
   还是默认按规范的"全部可安全重发"也重发新单（两者都实现，只问默认值）。
4. 锁步模式的控制通道放在同进程（SPSC + eventfd，服务端与客户端两个线程）：锁步只是验证模式，不需要跨进程；
   `lob_ouch_server` 另提供独立进程运行方式，用于手工 / 自由运行的回环测试与 tick-to-trade 测量。

## 7. 实现补记（2026-11-05，L4 完成时）

与上文设计相比的偏离与补充，全部写入了 DECISIONS（D-059–D-064）与 MODULE_NOTES/L4.md：

1. **同一账户的第二个登录：接管而不是拒绝**（§2.5）。客户端重连时服务端可能还没察觉旧连接断开，拒绝会让客户端进入终态 `Rejected`。
2. **屏障按连接计数**（§4.1）。断线时在途的入站消息可能永远到不了交易所，按账户累计计数的屏障会永远等不到——由自由运行的故障注入测试发现。
3. **只在我方有在途订单时才把行情事件发给交易所**（锁步）：没有订单就不可能成交，屏障数随之减少；锁步结果不变（逐位相同）。
4. **独立进程的 `lob_ouch_server` 推迟到 L5**（§5 L4.3）：两个进程需要共享行情，正是 L5 的组播。
5. **tick-to-trade 的"先发后做"**（§3.1）：本帧订单发出之后才转发行情、读回报；并增加"本帧第一条消息"的口径（做市改价先撤后挂）。
   交易所服务端增加可选的忙轮询（`busy_poll`），实测回环的主要代价是唤醒对端线程（BENCHMARK §15）。
6. **客户端会话增加终态 `Failed`**（Login Accepted 的序号或会话与请求不符），不自动重连（§2.5 原文的"告警 + 熔断"）。
7. OUCH 消息结构体的字母字段默认为空格（全 NUL 在线上非法）。
