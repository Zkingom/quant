# L5 设计：UDP 组播与 A/B 双路仲裁

> 状态：**设计待确认**（2026-11-05）。确认前不写实现代码。
> 范围：MoldUDP64 A/B 组播回放发送器（可注入丢包、乱序、重复、延迟）；接收端仲裁（去重、补洞）；两路都缺时向最小 MoldUDP64
> 重传服务请求；接入流水线取代文件输入；tick-to-trade 扩展为"收到 UDP 包 → 发出订单"。不改动 L1 冻结语义；L3' / L4 的接口只增不改。
> 依据：Nasdaq **MoldUDP64 Protocol Specification v1.00**（2026-11-05 下载核对）。规范未写的地方标为【本项目约定】。

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 为什么要 A/B 两路 | UDP 组播不重传：交换机缓冲溢出、网卡 / 内核接收队列满都会丢包。交易所把**同一个**序号流在两条物理独立的路径上各发一遍，接收端谁先到用谁，丢包率从 p 降到约 p²（两路独立时）。 |
| 仲裁的本质 | MoldUDP64 的序号是**消息级**的（包头给出第一条的序号，其余隐含递增），所以仲裁按消息序号做：对每个序号，第一次到达的那份被交付，之后的副本丢弃；交付严格按序号连续。 |
| 两路都缺 | 先等一个**有界的仲裁窗口**（另一路可能稍晚到）；超时后向重传服务发 Request Packet（会话 + 起始序号 + 条数），最小化请求范围；重传也超时 / 失败 → 交给现有的 `FeedHandler` 恢复状态机（`Recovering` → `Stale`），绝不跳过缺口继续发布。 |
| 硬门槛 | 任意**可补齐**的故障组合（丢包、乱序、重复、延迟，两路任意组合，只要每条消息至少在 A、B、重传之一里到达）下，交付给流水线的消息序列与**直接读文件逐字节相同**，于是事件流哈希与快照哈希相同。补不齐时：走恢复，最终状态可解释（Stale 或恢复成功），不发布错误的订单簿。 |
| 可验证性 | 仲裁器写成 sans-IO（包字节 + 时间进，有序消息 + 重传请求 + 超时点出），状态机每个转换有具名测试；故障注入按种子生成，矩阵覆盖"丢包率 × 乱序深度 × 重复率 × 延迟 × A/B 组合"；真实 socket 的回环组播测试另跑（进 TSan）。 |
| tick-to-trade | t0 从"ITCH 帧开始解码"前移为"`recvmmsg` 返回这个 UDP 包"，即 T0' 收到包 → 仲裁 → 解码 → … → `send()`；仲裁本身单独报告一段。 |

## 1. MoldUDP64（规范要点，L5 只用到这些）

- **下行包**（组播；或对重传请求的单播应答）：Session 10（字母数字）· Sequence Number 8（包中第一条消息的序号）· Message Count 2；
  其后 Message Count 个消息块（Message Length 2 + 数据）。Message Count = 0 是**心跳**，0xFFFF 是**会话结束**；两者都携带"下一个期望序号"。
- 心跳通常每秒一次（规范原文 "typically"）：低流量时让接收端也能发现**尾部丢包**（最后几条丢了，后面又没有新消息时，只有心跳的序号能暴露缺口）。
- **请求包**（单播到重传服务器）：Session 10 · Sequence Number 8（第一条请求的序号）· Requested Message Count 2。应答是普通下行包，单播回请求来源；
  从组播 socket 发出请求，就能在同一个 socket 上收到应答（规范建议的用法）。
- 会话结束包持续发送一段时间，期间仍可补请求——这是最后的补洞机会。
- 现有代码：`include/lob/md/mold.hpp` 已有下行包解析（L3' 1d，含截断、零长度、尾部多余字节的错误码）；L5 补编码器与请求包。

## 2. 真实系统里怎么做（设计依据）

- **A/B 物理隔离**：两路走不同的交换机、不同的网卡（常见是两块网卡各接一路）。同一机器上两路的到达时间差通常是微秒级，偶发毫秒级。
- **仲裁位置**：在行情处理器最前端，一个线程（或网卡旁路的轮询线程）同时收两路；先到先用；仲裁之后才有"一个序号流"的概念。
- **缺口不是立刻请求**：另一条线可能马上补上；请求太早浪费重传服务器的容量（交易所对重传请求通常有速率限制），太晚则延迟订单簿。
  常见做法是等一个以微秒到毫秒计的窗口，期间继续缓存后续消息（**不能**交付，交付必须按序）。
- **重传服务器有容量上限**：只保留最近一段消息；太旧的缺口要用快照服务（Nasdaq 的 GLIMPSE）重建订单簿——这正对应现有的 `Recovering`
  状态与可注入的重同步源（D-049）。L5 实现最小重传服务（保留全部或最近 N 条）；快照重建沿用现有接口，不在 L5 新做。
- **内核接收队列**：组播丢包最常见的地点之一是自己机器的 socket 接收缓冲区（`SO_RCVBUF`）。接收线程必须比发送端快，且缓冲区要够大；
  `recvmmsg` 一次系统调用收多包。L5 统计并报告内核丢包（`SO_RXQ_OVFL` 计数）。

## 3. 组件

```
文件 ─▶ 发送器（sans-IO 打包 + 故障注入器）─▶ UDP 组播 A ─┐
                                        └─▶ UDP 组播 B ─┤
                                                         ▼
                                       接收线程：recvmmsg(A, B) ─▶ Arbiter（sans-IO）─▶ 有序消息 ─▶ 解码 ─▶ SPSC ─▶ 订单簿线程 …
                                                         ▲                 │ 缺口超时
                                       重传应答（单播）──┘                 ▼
                                                                     Request Packet ─▶ 重传服务（sans-IO 核心 + UDP 驱动）
```

1. **MoldUDP64 编码**（`lob::md::mold`）：下行包编码器（按最大负载切包，【本项目约定】默认 1 400 字节，不超过以太网 MTU）、请求包编解码。
2. **发送器**：读文件（或内存）里的 ITCH 帧，打成 MoldUDP64 包；同一个包序列送 A 和 B 两路；按配置发心跳与会话结束。
3. **故障注入器**（每路独立、按种子确定）：丢包（概率 / 突发丢 k 个）、乱序（在深度 d 的窗口内打乱）、重复、延迟（固定 + 抖动）、
   以及"某段序号两路都丢"（强制走重传）与"重传服务也没有"（强制走恢复）。注入作用在**包**上（真实网络丢的是包，不是消息）。
4. **仲裁器 `Arbiter`（sans-IO）**：输入 = (路标识, 包字节, 当前时间)；输出 = 按序交付的 `(seq, 消息字节)`、要发的重传请求、下一个超时点、事件计数。
5. **重传服务 `Rewinder`（sans-IO 核心）**：持有已发送消息（全部或最近 N 条）；按请求返回下行包（受最大包长约束，可能分多包）；超出保留范围或会话不对 → 不应答（规范没有"拒绝"消息）。
6. **接入流水线**：新增 `ChunkSource` 的兄弟接口——**消息源**（直接给出 `(seq, payload)`，已经有序），解码线程从它取消息，后面不变。
   `FeedInput.seq` 用 MoldUDP64 的消息序号（第一条为 1），与文件回放时的帧序号一致，所以下游哈希可以直接比较。

## 4. 仲裁器状态机

每个序号只有三种状态：已交付（< `next`）、已缓存（在重排缓冲区里）、缺失。仲裁器整体状态：

```
          ┌──────────── 收到 next 或其后连续的消息：交付，next 前进 ────────────┐
          ▼                                                                  │
      InSync ── 收到 > next 的消息（出现缺口）──▶ GapWait(t_gap)  ──另一路补上──┘
                                                │ 等到 t_gap + arbitration_window
                                                ▼
                                          Requesting(n 次) ── 重传补上 ──▶ InSync
                                                │ 每次超时：再请求（上限 r 次，退避）
                                                ▼
                                           Unrecoverable ── 通知下游 SequenceGap ──▶ 下游走 Recovering / Stale
                                                （仲裁器跳到缺口之后继续交付，交给 FeedHandler 判定，见 §5）
```

- **去重**：序号 < `next` 的消息直接丢弃（计数 `duplicates`）；已在缓冲区里的同序号副本丢弃。【本项目约定】同一序号两份内容不同 → 计数
  `conflicts` 并告警（真实系统中两路内容必须一致；不一致意味着上游错误），以先到者为准。
- **重排缓冲区**：固定容量（【本项目约定】默认 65 536 条消息，按序号环形索引），预分配，热路径不分配。缺口后面的消息先缓存；
  缓冲区满 → 立即按"补不齐"处理（不能无限等待）。
- **最小请求**：缺口 = `[next, 缓冲区中最小已收序号)`，请求只覆盖真正缺的连续段；多个缺口分别请求；Requested Message Count 是 2 字节，
  超长的缺口拆成多条请求。
- **心跳与尾部丢包**：心跳 / 会话结束包里的"下一个期望序号"大于 `next` 时，也等价于出现缺口。
- **会话**：两路的 Session 字段必须相同；收到不同会话的包 → 计数并丢弃（【本项目约定】不支持会话中途切换）。
- **超时用注入的时钟**：所有窗口与重试都由 `on_timer(now)` 推进；测试用假时钟，不 sleep。

## 5. 与现有恢复状态机的关系（不改 L3' 语义）

现有 `FeedHandler` 已经有序号缺口检测：遇到缺口进入 `Recovering`，向注入的 `RecoverySource` 请求补发，补不齐 → `Stale`（D-049）。L5 的分工：

- **仲裁器负责网络层的补洞**（A/B + 重传服务），目标是让下游**看不到**缺口：可补齐的故障下，下游收到的序列与文件完全一致，`FeedHandler` 永远 `Live`。
- **补不齐时，仲裁器不隐瞒**：跳过缺口继续交付，下游 `FeedHandler` 自己发现序号跳变 → `SequenceGap` → 走现有的恢复路径（`RecoverySource` 可以接
  快照服务；默认没有 → `Stale`）。这样"补不齐"的行为与 L3' 已测过的路径完全相同，不新增第二套恢复逻辑。

## 6. 可验证性

1. **硬门槛（等价）**：同一个 ITCH 文件，(a) 直接读文件回放；(b) 发送器 → 故障注入 → 仲裁 → 流水线。只要故障可补齐，(b) 交付的
   `(seq, 消息字节)` 序列与 (a) 的帧序列逐字节相同，因而事件流哈希、快照哈希、交易摘要全部相同。
2. **故障注入矩阵**（sans-IO，无 socket，确定、快）：种子 × {丢包 0 / 1% / 10% / 突发} × {乱序深度 0 / 4 / 64} × {重复 0 / 5%} × {延迟差 0 / 1 ms}
   × {只 A 有故障 / 只 B / 两路独立 / 两路同时丢同一段 → 走重传}；另有"重传服务也没有"的用例，断言下游进入 `Recovering` / `Stale` 且从不发布错误订单簿。
3. **仲裁器状态机**：每个转换一个具名测试（`InSync_OutOfOrderPacket_GoesGapWait`、`GapWait_OtherLineFills_GoesInSync`、
   `GapWait_WindowExpires_SendsMinimalRequest`、`Requesting_RetriesExhausted_GoesUnrecoverable`、`Heartbeat_AheadOfNext_OpensGap` 等）。
4. **真实 socket**：回环组播（`IP_MULTICAST_LOOP`，接口 127.0.0.1）+ 单播重传，发送线程、接收线程、订单簿线程，标签 `concurrency` 进 TSan；
   【本项目约定】环境不支持组播（加入组失败）时测试 `GTEST_SKIP` 并说明原因，sans-IO 矩阵照常运行（本容器已验证回环组播可用）。
5. **负对照**：故意让仲裁器"缺口超时后直接跳过"→ 等价测试必须失败；故意交付重复 → 哈希必须不同。

## 7. tick-to-trade 扩展

- t0' = 接收线程 `recvmmsg` 返回包含该消息的 UDP 包时的 TSC（同一个包里的多条消息共享 t0'）。
- 新增分段：**T_arb** t0' → 仲裁交付该消息（含等待另一路 / 重传的时间：正常无故障时只有处理开销）；之后沿用 L4 的 T1–T5。
- 报告两种情况：无故障；A 路丢 1%（B 补上）——后者显示仲裁的尾部代价。同样扣计时开销、标环境、待本机复测。
- 限制：回环组播不经过网卡和交换机，两路"物理隔离"在这里只是两个 socket；不能说明真实 A/B 的到达时间差。

## 9. 需要作者确认的点
