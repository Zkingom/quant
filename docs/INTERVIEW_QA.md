# 面试问答：L3' 行情流水线、确定性、延迟测量与风控

> 写给大二同学：假设你学过 C++ 和操作系统的基本概念（线程、缓存、系统调用），但没做过交易系统。
> 每个问题先讲直觉，再讲本项目里具体怎么做、代码在哪、怎么验证。文件路径都相对仓库根目录。

## 1. SPSC 队列里的 memory order 为什么这样选？

**直觉。** 两个线程共享一块环形数组：生产者往里写，消费者往外读。CPU 和编译器为了快，会把内存操作"重新排序"——
你在代码里先写数据、再改下标，别的核上看到的可能是"下标先变了、数据还没到"。memory order 就是告诉编译器和 CPU："这里不许乱排"。

**我们的规则**（`include/lob/concurrent/spsc_queue.hpp`）：

| 操作 | order | 为什么 |
|---|---|---|
| 生产者读自己的 `tail`、消费者读自己的 `head` | `relaxed` | 只有自己写这个变量，自己读自己的写入永远是最新的，不需要和别人同步 |
| 生产者写完槽位后 `tail.store(..., release)` | `release` | "release"像是发货时贴封条：封条之前写的东西（槽位里的数据），对方拆封后一定看得见 |
| 消费者 `tail.load(acquire)` | `acquire` | "acquire"是拆封：看到新 tail，就保证看到完整的数据 |
| 消费者读完槽位后 `head.store(..., release)`；生产者 `head.load(acquire)` | 一对 | 反方向同样的道理：保证消费者已经把旧数据读走，生产者才覆盖这个槽 |

**为什么不用 `seq_cst`（最强的顺序）？** 它额外保证"所有线程看到的所有原子操作有一个统一的全局顺序"。我们只有两个"单写者、单读者"的标志，
没有第三个线程需要比较 head 和 tail 谁先变，所以 release/acquire 已经足够，`seq_cst` 只会多付代价（x86 上 store 要加一条 `mfence` 级别的指令）。

**还有两个细节：**
- head 和 tail 放在**不同的缓存行**（64 字节对齐）。否则两个核反复写同一缓存行，会发生"伪共享"：缓存行在两个核之间来回搬运，非常慢。
- 每一侧还缓存一份对方的下标（`cached_head` / `cached_tail`），只有在"看起来满了 / 空了"时才去读对方的缓存行，减少跨核流量。

**怎么证明没写错？** 在 x86 上，就算你把 release 改成 relaxed，程序大概率照样"能跑"（x86 是强内存模型，TSO）。所以光靠运行结果证明不了。
我们用 ThreadSanitizer（TSan）：它按 C++ 内存模型检查"有没有两个线程在没有同步的情况下访问同一内存"。我们手工把三处 order 分别改弱，
TSan 三次都报了 data race（MODULE_NOTES/L3 §1a）。这叫**负对照**：证明测试有能力发现错误。

## 2. 多线程了，结果怎么还能和单线程逐字节一样？

**直觉。** 多线程结果不确定，通常是因为"谁先谁后"取决于调度。如果数据只沿一条线流动、每一段只有一个人处理、而且不丢不乱，那顺序就是固定的。

**本项目的三个条件**（`include/lob/pipeline/pipeline.hpp`）：
1. **唯一生产者、唯一消费者、FIFO**：解码线程按文件顺序产生消息，SPSC 队列先进先出，订单簿线程按同样顺序处理。
2. **无损背压**：队列满了生产者就**等**，不丢消息（D-048）。如果满了就丢，结果就取决于消费者当时快不快。
3. **决策不读墙钟**：策略的定时器、风控的令牌桶都用 ITCH 消息里的时间戳，而不是 `now()`。计时只用来**测量**延迟，不影响任何决定。

还有一点很关键：单线程模式和多线程模式**调用的是同一个 `BookStage::consume` 和同一个下游**，不是两份写法相似的代码。

**怎么验证？** 不是靠论证，而是靠测试：3 个种子 × 4 种队列容量（容量 1 会让两个线程几乎每条消息都交接一次）× 2 种读取粒度，
事件流文本、哈希、订单簿哈希全部相等；交易部分的订单、成交、持仓哈希也相等（`tests/pipeline/`、`tests/trading/`）。
再把某个种子的哈希写成常量，GCC 和 Clang 的 Debug / Release / ASan 必须得到同一个数——这也顺带证明了没有依赖未定义行为或编译器差异。

**策略、风控、交易所为什么不各开一个线程？** 如果交易所单独一个线程，成交回报"什么时候回来"就取决于调度，同一份行情可能产生不同的成交顺序，
回测和实盘就对不上了（D-052）。

## 3. 跨线程测延迟，偏差从哪里来？

**直觉。** 测一段代码多久，就是"结束时刻 − 开始时刻"。但如果开始在核 A 上读时钟、结束在核 B 上读时钟，两个核的时钟要是不完全对齐，差值就带着误差。

**我们怎么测**（`include/lob/pipeline/clock.hpp`，BENCHMARK §13）：
- 用 CPU 的时间戳计数器 TSC（`rdtsc` 指令，读一次约 6–7 ns），启动时和 `steady_clock` 对比算出"每个 tick 多少纳秒"。
- **计时本身有开销**：读两次时钟就要约 13 ns。我们先测"背靠背读两次"的中位数，从每个样本里减掉，减完小于 0 就记 0。
- 每一"跳"（hop）单独记录：decode（解码）、queue（排队 + 跨核交接）、book（订单簿），阶段 3 再加 strategy / risk / engine。

**偏差的来源：**
1. **跨核 TSC 偏移**：queue 这一跳用两个核的 TSC 相减。CPU 标志 `constant_tsc` / `nonstop_tsc` 保证频率恒定，内核开机时也检查同步性，
   但在虚拟机（WSL2、云主机）里，客户机无法验证宿主怎么调度 vCPU。这个偏差**减不掉**，只能声明。
2. **虚拟化噪声**：vCPU 可能被宿主暂停几十微秒，所以 p99.9 和 max 只能当作上界。
3. **"排队"不是"延迟"**：如果解码线程一直全速跑，队列总是满的，queue 跳测到的是 1.7 ms 的排队时间——这说明背压在起作用，
   不能说"跨线程要 1.7 ms"。所以我们同时报告"饱和"和"限速（每微秒一条）"两种模式；限速时 queue 的中位数约 350 ns，才接近交接成本（D-049）。
4. **冷缓存效应**：限速模式下消费者两条消息之间空等约 1 µs，缓存和分支预测器"变冷"，book 跳的中位数比单线程高十倍。这是真实效应，不是计时误差。

**一句话：** 测延迟时要说清楚测的是哪一段、在什么负载下、减掉了什么、减不掉什么。

## 4. 缺口恢复状态机是怎么设计的？

**问题。** 行情是"增量"的：只告诉你"订单 7 成交了 40 股"，而不是整本订单簿。如果中间丢了一条消息（比如"新增订单 7"），
后面关于订单 7 的消息就全都对不上，订单簿就错了。错的订单簿比没有订单簿更危险——策略会照着错的价格下单。

**状态**（`include/lob/md/feed.hpp`）：

```
Uninitialized --(收到本股票的 Stock Directory)--> Live
Live --(序号跳了)--> Recovering --(重传补齐)--> Live
                               \--(补不齐)------> Stale
Live --(时间戳倒退 / 订单簿拒绝某条消息 / 解码失败 / 分帧失败)--> Stale
Stale --(加载快照)--> Live
```

**交易阶段（与上面的状态正交）：** 除了"订单簿对不对"，还要知道"市场现在开不开"。我们跟踪两条消息：
System Event（S）告诉你全市场处于哪个时段（O 开始、S 系统开始、Q 开盘、M 收盘、E/C 结束），Stock Trading Action（H）告诉你这只股票是在交易（T）、
停牌（H）、暂停（P）还是只报价（Q）。只有"开盘时段 + 正在交易"时才强制"买价 < 卖价"；盘前、集合竞价、停牌时买卖单可以合法地交叉
（大家在等撮合），这时订单簿照常维护、只计数并在每个事件上标记 `cross=X`，不判为错误。等到恢复交易的那一刻，交叉应该已经被撮合消除；
如果还交叉，先别急着判错——这是我们用真实数据踩到的坑（D-055）：2019-01-30 的 SXTC 在 LULD 暂停后恢复交易时，交易所先发停牌撮合的汇总成交（Q），
同一时刻发"恢复交易"（H 'T'），而参与撮合的那些订单各自的成交回报要在 'T' **之后**才陆续到达（约 0.25 ms 内）。只看 'T' 那一瞬间，订单簿是交叉的；
按旧规则立刻判 Stale，这只股票当天就再也用不了了。所以我们加了"宽限"：进入交易时段时订单簿还交叉，就先等着（不可交易），
直到交叉被消除**并且**看到了这只股票的撮合成交（证明交叉是撮合造成的、会被解决），才开始严格检查；等了 1 秒还没好，才判 Stale。
没收到过 H 的股票按"不在交易"处理，宁可不报价，也不在不知道状态时冒险。

**关键规则：**
- **不是 Live 就不发布订单簿**。下游只收到"状态变了 / 告警"，必须当订单簿不可用。
- 订单簿一旦拒绝过一条消息（比如引用了不存在的订单、数量会变负、新订单会和对面交叉），就再也不用了，直到快照替换它。
- 怎么发现丢消息：**序号**。样本文件里每条消息的位置就是序号；真实组播用 MoldUDP64，包头带序号（我们实现了它的解析，并用手工包测了丢包）。
  还有"语义缺口"：时间戳倒退、引用未知订单号。
- 序号**变小**（重复）不算错误，直接丢弃——真实系统常常同时收 A/B 两路相同的组播。
- 时间戳**向前大跳**不算丢失：收盘前后本来就可能很安静。丢没丢看序号，不看时间。
- 恢复手段可注入：`RecoverySource::retransmit`（重传缺失区间）或 `resync_from_snapshot`（整本快照）。默认没有，就一直 Stale 到收盘并告警。

**怎么测？** 手写的事件流 Golden；删掉一条、删掉一段、重复一条、时间倒退、四种订单簿拒绝；fuzz（随机翻转比特、插入删除字节）2 万次，
断言"订单簿永远一致、非 Live 从不发布"；每个字节位置截断一次。

## 5. 风控和熔断的语义是什么？

**事前风控**：订单发出去之前检查，不通过就拒绝（`include/lob/risk/risk.hpp`）。顺序是固定的，第一个不满足的就是拒绝原因：

1. **熔断开关**——打开了就拒绝一切新单；
1b. **交易阶段**——停牌、暂停、盘前盘后、盘口锁定 / 交叉时拒绝新单（NotTrading）。注意它**不触发熔断、也不计入"拒单太多"**：
   停牌是正常的市场状态，恢复交易后应该自动接着做；而熔断是"系统可能坏了"，必须人工确认后才能恢复。把两者混为一谈，
   要么每次停牌都要人工复位，要么熔断变得可以自动恢复——都不对；
2. **参考价**——订单簿必须 Live 且有买有卖（否则下面的价格带没法算）；
3. **乌龙指（数量）**——单笔数量上限，防止多打几个 0；
4. **乌龙指（金额）**——单笔价格 × 数量上限；
5. **价格带**——离中间价不能超过 1%（可配），防止价格打错一位；
6. **最大持仓**——按最坏情况算：当前持仓 + 所有同方向还没成交的单 + 这一单，全部成交也不能超限；
7. **报单频率**——令牌桶：桶里最多 N 个令牌，每秒补 R 个，每单花一个。用整数定点数实现，长时间不报单也不会溢出。

**撤单永远放行**——包括熔断时。熔断的目的是降低风险，而撤单就是降低风险的手段，拦住它反而危险。

**熔断（kill switch）的语义：**
- **有粘性**：触发后一直保持，直到人工 `reset()`。即使触发的原因消失了也不会自动恢复——自动恢复会让一个坏掉的系统反复开关。
- 自动触发：订单簿离开 Live（StaleBook）；短时间内被拒太多次（RejectStorm，说明策略可能失控）。也可以人工触发。
- 触发后立刻撤掉所有挂单。

**它有多快？** 单次检查约 8 ns（云端，待本机复测），因为全是整数比较，没有分配、没有锁。

## 6. 为什么 CI 用"指令数"做性能门槛，而不是测时间？

**问题。** CI 跑在共享机器上，同一个程序这次 10 ms、下次 13 ms 很正常。本项目在 WSL2 上的 A/B 测试就规定"±10% 以内算噪声"，
在云端我们甚至看到同一程序两次会话吞吐差了 2 倍。拿时间做门槛，要么天天误报，要么阈值宽到什么都抓不住。

**做法**（`scripts/icount_gate.sh`、`bench/itch_icount.cpp`，D-051）：
- Valgrind 的 cachegrind 像一个"模拟 CPU"，可以**精确数出**程序执行了多少条指令（Ir）。同一个二进制、同样的输入，每次数出来**完全一样**。
- 只数被测的那一段（用 cachegrind 的开关宏，把"生成测试数据"排除在外），三个固定场景：解码、订单簿回放、交易。
- 和仓库里的基线比，多了 2% 以上就失败。

**它的局限要说清楚：** 指令数不等于时间。缓存没命中、分支预测失败、多线程交接，指令数都看不出来。它能抓的是"代码多做了活"这种回归，
抓不到"同样多的指令但内存访问变差了"。所以墙钟基准仍然要在本地按 BENCHMARK 的方法跑。

**为什么要固定编译器？** 换个编译器版本，生成的指令就不一样，数出来自然不同，那不是回归。所以基线文件记下编译器、valgrind、glibc 版本，
对不上就拒绝比较（退出码 3），而不是报一个假回归。基线由改动的作者在同一个 PR 里更新，写明原因，审阅者批准。

**我们验证过门槛有效：** 往 `md::Book::add` 里塞 40 次空循环，book 场景 +1.9%（没超阈值，放行）；塞 200 次，+9.3%，门槛失败。

## 6b. 全市场 8 700 只股票，怎么多线程又不失确定性？

**直觉。** 每只股票的订单簿只取决于"这只股票自己的消息"加上"全市场的时段消息"。只要每只股票收到的消息序列在各种模式下都一样，
它的结果就一样——与哪个线程处理、线程之间谁快谁慢无关。

**做法**（D-056）：一个路由器按消息里的股票编号（locate）分发：`locate % N` 决定去哪个工作线程，同一只股票永远在同一个线程；
时段消息（S）和流级故障广播给所有线程，因为路由器按原始顺序发出、每个队列先进先出，所以每只股票看到的广播位置也固定。
最后把每只股票的哈希加起来（加法与顺序无关）得到全市场汇总哈希。真实全天数据：单线程和 4 线程的 8 713 只股票哈希逐行相同。

**全市场也要零分配怎么办？** 先测量：三个交易日每只股票的价位数峰值中位数只有 35，最大的 AAPL / AMZN 是 3 000–4 200。于是按每只股票自己的峰值 × 2
预先分配并设为上限（共约 50 MB，统一按最大值则要 1.8 GB），回放前就把股票建好；某只股票当天超过上限，就让它变成 Stale 并报出来，而不是偷偷分配（D-058）。

**内存怎么控制？** 订单号全天全市场唯一，所以一个分片的所有股票共用一个订单池和一个"订单号 → 订单"索引，按全市场峰值在途订单数配置
（实测峰值 174 万单）；每个订单记住自己属于哪只股票，别的股票的消息碰不到它。

## 7. 十道追问题与参考要点

**Q1. 如果把 SPSC 改成多生产者（MPSC），哪里会坏？**
要点：`tail` 不再是单写者，两个生产者可能读到同一个 tail、写同一个槽。需要用 CAS（`compare_exchange`）抢槽位，
或每个槽带序号（Vyukov 队列）；"写完数据再发布"也要按槽单独发布，否则消费者可能读到别人还没写完的槽。本项目的做法是"每个生产线程一个 SPSC"（异步日志就是这样）。

**Q2. 为什么队列下标用不回绕的 64 位计数器，而不是 `% capacity` 回绕？**
要点：满 / 空判断变成 `tail - head == capacity` / `tail == head`，不用浪费一个槽，也不用额外的标志位；容量是 2 的幂，取槽位用 `& mask`。
64 位每纳秒加一也要 500 多年才溢出。

**Q3. 行情回放时，为什么不能用 `mmap` 把整个文件映射进来？**
要点：可以，但驻留内存会随读过的页增长（虽然可回收），作者机器只有约 5 GB，文件有数 GB；用固定 1 MiB 缓冲区 `read()`，
峰值内存只由配置决定（实测 33 MB / 328 MB / 984 MB 输入都是约 47 MB），还能从管道读（边解压边回放）。代价是一次额外的拷贝。

**Q4. 订单簿为什么要"先校验后修改"？**
要点：一条消息被拒时订单簿必须保持原样，才能精确断言"拒绝没有副作用"，也才能在诊断时知道订单簿处于哪个已知状态。
例如 replace 要先确认原单存在、新 ref 不重复、新价格不交叉、价位容量够，全部通过后才删旧加新。

**Q5. 为什么 ITCH 的订单簿不能直接复用 L1 的撮合引擎订单簿？**
要点：L1 的 `OrderBook` 只能成交队首、没有部分撤单、要求 seq 递增和价格带；ITCH 的成交可以指向任意订单（交易所告诉你成交了哪一单），
部分撤单很常见。重建器只"照做"交易所说的事，不自己撮合。

**Q6. 乐观和保守两个成交模型，为什么说只对"相同订单流"构成上下界？**
要点：逐笔看，乐观模型每次给的成交 ≥ 保守模型，累计也 ≥（归纳）。但做市策略会根据成交调整库存偏移，两个模型下它后面发出的订单不同，
比较的就不是同一批订单了——我们实测过闭环下保守模型总成交量反而更大。所以测试用一个"挂一次、永不改价"的策略验证上下界。

**Q7. CRTP 和虚函数测出来差不多，那 CRTP 还有什么意义？**
要点：间接调用的目标固定时，分支预测器能准确预测，调用本身只有 1 ns 量级；这个策略每次要 12 ns，差别被掩盖。
CRTP 的真正好处是编译器能内联、能跨调用做常量传播和消除死代码，策略越小、调用越频繁越明显。不要声称没测出来的收益。

**Q8. 热路径"零分配"是怎么测出来的？为什么重要？**
要点：在专用测试程序里替换全局 `operator new`（含对齐版本），每个线程在热循环开始时"布防"，期间任何分配都计为违规；
再做一个故意分配的下游作为负对照，确认能抓到。分配可能走到锁或系统调用，延迟不可预测，还可能失败；预分配让最坏情况可控。
注意 L1 撮合引擎每次挂单都会分配，所以它不在这个保证里，文档里写明了。

**Q9. 令牌桶为什么用 ITCH 时间补充令牌，而不是系统时间？**
要点：用系统时间，同一份行情在快机器和慢机器、单线程和多线程下补充的令牌数不同，风控结果就不确定，回测也没法复现。
用行情时间，风控是输入的纯函数。代价是：如果行情时间和真实时间偏离很大（比如回放加速），频率限制的"每秒"指的是行情的每秒。

**Q10. 真实行情里，盘口出现"锁定 / 交叉"（买价 ≥ 卖价）时你的系统怎么处理？**
要点：先问"现在是什么时段"。集合竞价、停牌、暂停、盘前盘后，交叉是合法的，只在常规时段且个股为交易状态时强制"永不交叉"（D-054）。
再问"消息的到达顺序是什么"：真实数据里恢复交易的状态消息先到、撮合的逐笔成交后到，所以进入严格模式时要有一个**有界的宽限**——
等交叉被消除且看到撮合成交，最多 1 秒（D-055）。追问"宽限会不会掩盖真正的错误"：宽限要求看到 Cross Trade 作为证据、有时间和消息数上限、
宽限中不可交易；没有撮合证据的交叉在 1 秒后照样判 Stale。追问"上限怎么定"：实测 233–264 µs，留了约 4 000 倍余量，但只来自一只股票的两次恢复，
是需要更多数据复审的参数——这正是先测量、再定规则、并写明依据的例子。

**Q11（追加）. 全市场分片为什么按股票编号取模，而不是按负载动态分配？**
要点：取模让"哪只股票在哪个线程"只取决于输入，结果可复现、可对拍；动态分配要在运行中迁移股票的订单簿，迁移时机依赖调度，确定性和测试都更难。
代价是负载可能不均（实测 4 个分片峰值订单 40–47 万，较均匀）；热门股票集中时可以离线按历史量预先分配一张固定映射表，仍是确定的。

**Q12（追加）. 看 README 的 SXTC 时间线图，讲讲为什么需要"恢复宽限"。**
要点：暂停期间买卖单不撮合，最优买价可以高于最优卖价（灰色区域）。恢复时交易所先撮合，再宣布恢复交易，但每一笔参与撮合的订单的成交回报
要在 0.23–0.26 ms 后才陆续到达；在这段斜线区域里订单簿"看起来"交叉。宽限规则等它消除（且看到撮合成交的证据）再开始严格检查，
否则就会把一个正确的订单簿判成错误的。图下注明了数据来源与代码版本，任何人可以用脚本重新生成。
