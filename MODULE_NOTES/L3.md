# L3'：行情层、流水线、策略与风控

> 范围与门槛见 ROADMAP §2.3（D-046）。本文件按子阶段记录实现、证据与遗留问题；阶段完成即更新。
> 开发与测量环境：云端容器（4 vCPU，Linux 6.18，GCC 13.3，Clang 18.1.3），**不是**作者的 WSL2；墙钟数字只用于验证方法。

## 1a 无锁 SPSC 环形队列（`include/lob/concurrent/spsc_queue.hpp`）

- 容量为 2 的幂；索引为不回绕的 64 位计数器，`tail - head == capacity` 即满，不浪费槽位。
- 布局：生产者侧（`tail` + 生产者私有的 `cached_head`）、消费者侧（`head` + `cached_tail`）、只读区（`mask`、缓冲区指针）
  各占一个 64 字节缓存行（`static_assert` 固定）。只有缓存副本判定"满"或"空"时才读对方的缓存行。
- memory order（理由在代码注释中逐条写明）：
  | 操作 | order | 配对 |
  |---|---|---|
  | 生产者读自己的 `tail`、消费者读自己的 `head` | relaxed | 单写者读自己的写入 |
  | 生产者写槽位后 `tail.store` | release | 消费者 `tail.load(acquire)`：看到新 tail 即看到完整元素 |
  | 消费者读槽位后 `head.store` | release | 生产者 `head.load(acquire)`：覆盖槽位前，消费者的读已完成 |
  | 不使用 seq_cst | — | 只有两个单写者单读者的"消息传递"标志，没有第三方观察两个索引的相对顺序 |
- 元素必须 trivially copyable（`static_assert`）；构造后不再分配。

**测试**（`tests/concurrent/test_spsc_queue.cpp`，标签 `concurrency`，11 个）：容量校验、空/满、容量 1、多次回绕；
与容量受限的 `std::queue` 单线程对拍（5 种容量 × 5 个种子 × 20 000 步，逐返回值逐元素比较）；
双线程压力（容量 1/2/64/65536，Release 下最多 200 万个 32 字节元素，元素带校验字段以检出撕裂读；
与 `std::queue` 交付的序列逐元素比较）；随机突发长度的双线程测试（覆盖不同填充水平下的刷新路径）。

**TSan 负对照**（gcc-tsan，`TSAN_OPTIONS=halt_on_error=1`，手工逐一注入后恢复）：

| 变异 | 结果 |
|---|---|
| `tail.store` release → relaxed | `ThreadSanitizer: data race`，检出 |
| `head.store` release → relaxed | 检出（退出码 66） |
| 生产者刷新 `head` 的 acquire → relaxed | 检出（退出码 66） |

说明 TSan 压力测试对这三处 order 是敏感的；在 x86 上这些变异不会产生可观察的错误结果（TSO），只有 TSan 的模型能发现。

## 1b ITCH 5.0 子集解码器（`include/lob/md/itch.hpp`、`src/md/itch.cpp`）

- 分帧：样本文件为"2 字节大端长度 + 消息"。`FrameCursor` 在调用方缓冲区上前进，返回指向原缓冲区的 `span`（零拷贝，测试断言地址相同）；
  不足一帧返回 `Truncated` 且游标不动（分块读取时把尾部带入下一块），长度 0 返回 `ZeroLength`。
- 解码：按规范偏移逐字段读取（大端字节拼装，不做类型双关、不假设对齐）。子集 9 种消息的规范长度（含 11 字节公共头）：
  S 12、R 39、A 36、F 40、E 31、C 36、X 23、D 19、U 35。
- 拒绝而不是崩溃：空载荷 `Empty`；未定义类型 `UnknownType`；长度不等于规范长度 `BadLength`；
  枚举越界（side ∉ {B,S}、printable ∉ {Y,N}、事件码 ∉ {O,S,Q,M,E,C}）或时间戳 ≥ 24 h `InvalidField`。
  子集外的 14 种 5.0 类型（H Y L V W K J h P Q B I N O）在规范长度下 `Skipped`，长度不对同样 `BadLength`。失败时输出参数不变（测试断言）。
- 测试（21 个）：每种消息一条按规范逐字段手写的十六进制字面量，同时钉住解码器与 testkit 编码器
  （`itch_builder.hpp` 用 `push_back` 顺序追加，解码器用固定偏移，两种写法独立）；最大字段值；每种子集类型长度 ±1；
  256 个类型字节全部分类；帧的截断、零长度、连续帧。

## 1c 订单簿重建器 `md::Book`（`include/lob/md/book.hpp`、`src/md/book.cpp`）

- 不复用 L1 `OrderBook`（D-046）：ITCH 的成交可以指向任意订单（不只是队首），有部分撤单，价格无价格带。
- 只按更新语义应用：add / execute（E 与 C 相同，成交价不改变订单簿）/ cancel（部分；撤到 0 即删除）/ delete / replace（保持方向、失去优先级、新 ref 排到新价位队尾）。不撮合。
- **先校验后修改**，被拒的消息不改变订单簿（测试比较前后 `state_hash`）。检查顺序固定（参考模型与之相同）：
  add：重复 ref → 数量 0 → 价格 0 → 锁定 / 交叉 → 订单容量 → 价位容量；execute / cancel：未知 ref → 数量 0 → 超量；
  replace：未知原 ref → 新 ref 重复 → 数量 0 → 价格 0 → 锁定 / 交叉 → 价位容量。
- 不变量（`find_invariant_violation()`，O(n)）：每侧价位严格有序、无空价位、层总量 = 订单剩余之和、层订单数、双向链表一致、
  索引指向每个订单、索引占用数 = 空闲链表外的节点数、**最优买价 < 最优卖价（永不锁定、永不交叉）**、数量 > 0。
- 存储：订单节点池（构造时按 `max_orders` 分配）、开放寻址索引（线性探测 + 回移删除，无墓碑）、每侧按价格排序的数组（最优价在末尾，
  靠近盘口的插入只移动少量元素），容量在构造时 `reserve`。**构造后任何操作都不分配**；容量耗尽返回 `OrderCapacity` / `LevelCapacity`。
- 测试（13 个）：语义单测、交叉与锁定、非队首成交、部分撤单、数量永不为负、重复 / 未知 ref、replace 失去优先级、容量、clear、
  哈希只依赖规范状态、索引在大量碰撞与删除下的一致性；与朴素参考模型 `testkit::ReferenceMdBook`（`std::map` + 线性扫描）的差分：
  20 次运行（10 个种子 × 正常容量 / 极小容量），每步比较返回码、BBO、订单数、不变量，小订单簿每步、大订单簿每 10 步比较全量哈希，
  每 50 步比较排队位置；断言 > 10 000 次成功应用与 > 5 000 次拒绝。

## 1d 缺口检测与恢复状态机（`include/lob/md/feed.hpp`、`src/md/feed.cpp`、`mold.hpp`、`stream.hpp`）

- 序号来源：文件回放为帧序号（从 1 连续，缺口只可能来自有损传输，例如解码线程到订单簿线程之间丢元素）；
  MoldUDP64 为包序号 + 包内下标（`mold.hpp`，只用于手工包，用来测试真实的序号缺口）。
- 状态机：
  ```
  Uninitialized --(本股票的 Stock Directory)--> Live
  Live --(序号缺口)--> Recovering --(重传补齐)--> Live
                                 \--(无重传源 / 不完整 / 补齐过程中出错)--> Stale
  Live --(时间戳倒退 | 订单簿拒绝 | 符号不符 | 解码失败 | 分帧失败)--> Stale
  Stale --(resync_from_snapshot)--> Live     （快照被拒 → Stale，订单簿清空）
  ```
- 非 Live 时不发布任何 BookUpdate，只发 StateChange / Alert（每个事件都带当时的 BBO，便于诊断）。订单簿一旦拒绝过消息就不再使用，直到快照替换。
- 序号小于期望值（重复）丢弃并计数，不改变状态（MoldUDP64 A/B 双路的常态）。时间戳对全流（所有股票）要求非递减；
  向前跳跃不视为丢失（安静时段正常），丢失由序号检测。
- 默认没有重传源：缺口 → Stale 直到交易日结束；`RecoverySource` 可注入，测试中用"重放缺失区间"模拟重传。
- 事件以 `append_text`（规范文本行）或 `hash_event`（逐字段 FNV-1a）输出，绝不按原始字节（有填充）。
- 测试（17 个）：手写的完整期望事件流（Golden）；目录到达前的订单不应用；无重传的缺口；重传补齐后订单簿与无缺口运行一致；
  不完整重传；重复序号；本股票与其他股票的时间戳倒退；四种订单簿拒绝（未知 ref、交叉、超量、重复 ref）后不再发布；符号不符；
  解码失败与分帧失败；快照恢复与被拒的交叉快照；分块解码在每个切分点与整块一致；MoldUDP64 头、心跳、会话结束、逐字节截断、
  尾随字节、零长度块，以及丢包产生的精确缺口区间。

## 1e 鲁棒性（`tests/md/test_md_robustness.cpp`、`tests/fuzz/`、`scripts/fetch_itch.sh`）

- 只用手工构造的样本：`testkit/itch_samples.hpp` 的样本会话，字节与事件流固定在 `tests/golden/itch/session.{hex,events}`（可审阅的文本）。
- 逐字节截断：流的每个前缀——在帧边界的前缀产生的事件是完整事件流的前缀，其余前缀以 `FrameError` 进入 Stale；每个前缀之后订单簿一致，
  且从未在非 Live 状态发布。每条消息载荷的每个截断长度都被解码器拒绝。
- 固定种子变异 fuzz（每个预设都跑；非 Sanitizer 20 000 次，ASan 4 000 次）：位翻转、改字节、插入、删除、改长度前缀、复制片段；
  断言订单簿一致、非 Live 不发布，并断言变异确实改变结果（> 50%）且多数被判为错误（> 1/3）。另对 256 种类型 × 0–64 字节随机载荷解码。
- libFuzzer 入口（`-DLOB_FUZZ=ON`，Clang，`scripts/fuzz_itch.sh`）：2026-11-04 在云端容器运行 60 s，680 121 次执行、新增 1 314 个覆盖单元、
  无崩溃（ASan + UBSan），peak RSS 410 MB。需要 `libclang-rt-18-dev`。
- 真实数据：`scripts/fetch_itch.sh` 用 curl 流式下载到 `data/itch/`（`.gitignore` 排除，可断点续传），`gzip -t` 流式校验；
  回放通过管道 `gzip -dc … | lob_itch --input -` 边解压边读，文件不进内存（阶段 2 写明内存上限）。

## 阶段 2 流水线与延迟（`include/lob/pipeline/`、`src/pipeline/`、`apps/lob_itch.cpp`、`bench/itch_bench.cpp`）

- 结构：`run_single`（一个线程）与 `run_pipelined`（调用线程解码 → `SpscQueue<Item>` → 工作线程跑 `BookStage`）共用同一个生产函数
  `detail::produce` 与同一个 `BookStage::consume`；`Item` = `FeedInput` + 两个时间戳（trivially copyable）。
- **确定性**：唯一生产者、FIFO、无损（满即自旋，D-048）、唯一消费者；下游不读时钟做决策。所以两种模式的事件流与最终订单簿逐字节相同。
- 测试（`tests/pipeline/test_pipeline.cpp`，12 个，标签 `concurrency`，六个预设 + 两个 TSan 预设）：
  - 3 个种子 × 4 种队列容量（1、2、64、16 384）× 2 种读取粒度（整块、每次 4 093 字节）：流水线与单线程的事件文本、事件哈希、订单簿哈希、
    帧数、计数器全部相等；单线程 977 字节读取也相等（分块拼接）；
  - 固定哈希常量（种子 42，5 000 条）：GCC 与 Clang、Debug / Release / ASan 必须得到同一常量；
  - 截断尾部、中间损坏的流在两种模式下结果相同；样本会话经流水线与 golden 事件文件逐字节一致；限速回放结果相同；
  - `FdSource` 读文件与内存源结果相同；读缓冲小于最大帧时拒绝配置；
  - 延迟记录器的分位数、开销扣除、钳 0、dropped；流水线三个 hop 都被记录；
  - 异步日志：两个线程两个通道各 500 条，通道内顺序与格式正确；未启动写线程时满即丢弃并计数；未知格式 / 缺参数可见。
- **零分配**（`tests/pipeline/test_pipeline_alloc.cpp`，独立可执行文件，`lob_testkit_alloc_guard` 替换全部形式的 `operator new`，
  包括对齐形式）：各线程在热循环开始时通过 `ThreadHooks` 布防、结束时撤防；布防线程上的任何分配都计为违规。
  单线程与流水线各回放 30 000 条（读取粒度 5 000 字节，带延迟采样）违规 0；异步日志入队 5 000 次违规 0；
  **负对照**：一个在热路径 `push_back` 的下游被检出（违规 > 10）。缺口重传会分配，不在热路径内（测试流无缺口）。
- 延迟瀑布与内存上限见 BENCHMARK §13（云端数字，待本机复测）。
- `lob_itch`：真实文件 / 管道回放（`--input -` 读标准输入），打印计数器、状态、事件与订单簿哈希、吞吐、延迟表、峰值 RSS 与配置上限。
  RSS 不随输入大小变化（33 MB / 328 MB / 984 MB 管道：约 47 MB）。

## 阶段 3 策略与风控（`include/lob/{strategy,risk,sim}/`、`src/{strategy,risk,sim}/`）

**数据流**（全部在订单簿线程上同步执行，D-052）：

```
BookStage ── FeedEvent ──▶ TradingStage::on_feed
                             1. SimExchange::on_market(e)   市场成交 → 我们挂单的成交 → OMS → strategy.on_fill
                             2. strategy.on_book_update(top) → 请求 → RiskGate::check_new → SimExchange::submit
                                                                     │                       └▶ L1 MatchingEngine::process
                                                                     └ 拒绝 → on_fill(qty 0, leaves 0)
                             3. ITCH 时间越过定时边界 → strategy.on_timer
                             feed 离开 Live → 熔断(StaleBook) → 撤全部挂单 → on_book_update(live=false)
```

- **策略接口**：`on_book_update / on_fill / on_timer`，只由 ITCH 时间驱动；输出写入定长 `Actions`（16 条，溢出计数，不分配）。
  热路径用 CRTP（`StrategyBase<Derived>`）；`VirtualStrategy` 是同一接口的虚函数版本，工厂函数放在单独的翻译单元，防止编译器去虚化。
  `on_fill` 也承载"订单结束未成交"（qty 0、leaves 0：风控拒绝、交易所拒绝、系统撤单）。
- **做市示例** `MarketMaker`：保留价 r = mid − skew × 库存，买卖价 = r ∓ 半价差，按 tick 取整并保持被动（买价 < 最优卖价、卖价 > 最优买价）；
  某侧库存达到上限即停止该侧报价；价格不变不重报；订单簿不可用时全部撤单。全部整数运算。
- **事前风控** `RiskGate`（顺序固定、可观察、有测试）：熔断 → 参考价（订单簿 Live 且双边）→ 乌龙指（数量）→ 乌龙指（名义金额）
  → 价格带（相对中间价，bps）→ 最大持仓（持仓 + 同向在途 + 本单的最坏情况）→ 报单频率（令牌桶，按 ITCH 时间补充，定点整数，长间隔饱和不溢出）。
  撤单从不被拦（熔断时也允许，降低风险必须总是可行）。熔断：`trip()` 有粘性，只能 `reset()`（人工操作）解除；
  订单簿离开 Live 自动触发（StaleBook），窗口内拒单数达到阈值自动触发（RejectStorm）；触发后撤掉所有挂单。
- **模拟交易所** `SimExchange`：风控通过的订单进入**未改动的 L1 `MatchingEngine`**（只用 `process(NewOrder / CancelOrder)`）。
  引擎里只有我们的订单；ITCH 的成交（E / C）被转成一笔反方向的合成限价单送入引擎，与我们价格不劣于成交价的挂单撮合（maker 价成交），
  剩余部分立即撤单（IOC）。合成订单 ID 在 2^62 之上，与客户订单 ID 分离。
- **两个成交模型**（同时运行两套策略 + 风控 + 交易所，`sim::Both`）：
  - 乐观：合成单携带该笔成交的全部 q 股——假设我们排在队首。
  - 保守：挂单时记录同价位已显示的总量（排在前面的量）与该价位最大的订单 ref（Nasdaq 的 ref 当日递增、replace 产生新 ref，
    所以 ref ≤ 该值的订单都在我们前面）。该价位的成交先消耗前面的量，只有超出部分才轮到我们；前面的订单撤单 / 删除 / 改价离开时前面的量减少，
    后面的订单撤单不影响。
  - 两个模型中，成交价比我们的价格更差（市场穿过了我们的价格）时，我们最多成交 q 股（对手方至少吃了 q 股，且会先碰到我们）；
    q 股作为预算按价格优先在我们的订单之间分配。由此逐笔归纳可证：**同一订单流下**，每张订单在乐观模型中的累计成交量不小于保守模型。
  - **重要限制**：上下界只对**相同的订单流**成立。会根据成交调整报价的策略（做市示例的库存偏移）在两个模型下发出不同的订单，
    总成交量不再有序——实测种子 8、40 000 条：乐观 280 636 股、保守 394 800 股（修正 trade-through 规则与生成器之前的版本中发现）。
    测试用一个"加入一次、永不改价"的策略验证上下界，并断言至少一个种子严格不等。两个模型都不模拟我们自己对市场的冲击。
- 阶段 3 中对已提交部分的改动（同一提交内，如实记录）：
  1. `FeedEvent` 增加 `side / price / shares / prev_*`（在应用消息**之前**查得被成交 / 撤单 / 替换的订单），事件文本格式扩展
     （`msg=`、`prev=`），`tests/golden/itch/session.events` 与 `test_feed` 的内联 Golden 随之更新，逐行人工核对；
  2. 合成流生成器原先随机选择被成交的订单，会在比最优价更差的价位成交——从我们报价的角度看全是"穿价"，两个模型因此无差别
    （测试发现）。改为只成交最优价位的队首订单（真实市场的行为）；阶段 2 固定的哈希常量随之更新。
  3. 保守模型的穿价规则最初给出"整张剩余量"，乐观模型给出 min(q, 剩余)，导致保守成交多于乐观（测试发现）；统一为 min(q, 剩余)。
- **测试**（`tests/trading/`）：风控 11 个具名测试（每项检查一个、熔断粘性、拒单风暴、窗口外不累计、检查顺序）；做市 6 个（偏移报价、只在变化时重报、
  窄价差下保持被动、库存上限、订单簿不可用时撤单、CRTP 与虚函数对 5 000 个随机盘口产生完全相同的请求）；成交模型 7 个（乐观队首、保守排队、
