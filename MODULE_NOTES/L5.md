## L5.0 范围与环境（2026-11-07）

**范围**：D-066 把范围从 L4 扩展到 L5（取代 D-065 中关于 L5 的部分）；L6 与独立进程的 `lob_ouch_server` 仍是未来计划（ROADMAP §2.6）。
D-067 记录设计 §9 的默认值：仲裁窗口 200 µs，重传超时 5 ms × 最多 3 次、指数退避，重排缓冲 65 536 条（满了按补不齐处理），
补不齐时跳过缺口交给 `FeedHandler`，组播不可用时真实 socket 测试跳过。

**WSL2 回环组播实测**（`python3 -I scripts/mcast_probe.py`，完整输出：`MODULE_NOTES/evidence/L5/mcast_probe_wsl2_2026-11-07.txt`）

| 检查 | 结果 |
|---|---|
| 两个组（239.255.0.1 / .2）在接口 127.0.0.1 上各收 200 个包（A/B 两路），`IP_MULTICAST_LOOP=1` | 3 次运行均 200/200，按序 |
| 收到组播包后向发送方地址回单播（MoldUDP64 重传请求 / 应答的路径） | 3 次均收到 |
| `lo` 的接口标志 | `<LOOPBACK,UP,LOWER_UP>`，**没有 `MULTICAST`**；不影响以 127.0.0.1 为接口加入组与发送 |
| 接收缓冲 | `rmem_default` = `rmem_max` = 212 992 字节（`SO_RCVBUF` 同） |
| 无读者时突发 100 000 个 1 008 字节的包 | 收到 93 个，丢 99 907 个；随后一个包携带的 `SO_RXQ_OVFL` 累计丢包计数 = 99 907，与实际相符 |

结论与对后续阶段的影响：
- 回环组播在本机可用，L5.4 的真实 socket 测试可以在本机运行（不需要替代方案）。环境不支持时（加入组播组失败）测试 `GTEST_SKIP` 并写明原因（D-067）。
- 内核接收缓冲只有约 200 KB，且提高 `rmem_max` 需要改系统设置（本项目不改）。发送端只要领先接收端约 200 个 1 KB 的包就会被内核丢弃，
  所以真实 socket 测试要得到确定的结果必须有流控（发送端领先量有上限）；具体机制在 L5.4 决定并写入 DECISIONS。
- `SO_RXQ_OVFL` 计数可靠，L5.4 用它统计并报告内核丢包。
- 限制：回环不经过网卡与交换机，A、B 两路在这里只是两个 socket（设计 §7）；mirrored 网络模式对回环时延的影响未测（L5.5 测量时注明）。
- GitHub Actions 的 runner（ubuntu-24.04，非 WSL）是否支持回环组播在 L5.4 的首次 CI 运行中确认并记录。

**其他**：本地 `main` 与 `origin/main` 分叉（本地有 5 个从未推送的旧 L3 网关提交，已被 D-046 废弃），本地 main 保存为分支 `backup/local-main-old-l3`

## L5.1 MoldUDP64 编码（2026-11-20）

**交付**：`include/lob/md/mold.hpp` 只增不改（原有 `Header` / `Status` / `parse_packet` 不变）：
- `PacketBuilder`：在调用方给的缓冲区里一次拼一个下行包，缓冲区大小即最大包长；`add()` 返回 `Ok` / `Full`（本包放不下，`finish()` 后重试）/
  `TooLarge`（任何包都放不下，或长于 65 535 字节）/ `ZeroLength`；非 `Ok` 时状态不变。`finish()` 写包头并从下一个序号开始新包。每包最多 0xFFFE 条。
- `packetize()`：把一串消息贪心地切成包（每包尽量装满）；遇到无法成帧的消息时先发出它之前的全部消息再停，返回失败位置与原因。
- `encode_heartbeat()` / `encode_end_of_session()`：只有包头，序号为下一条要发的消息序号（规范的约定）。
- `Request` / `encode_request()` / `parse_request()`：20 字节请求包；长度不对返回 `Truncated` / `TrailingBytes`，条数为 0 返回 `ZeroCount`。
- 全部只写调用方缓冲区，不分配内存。约定见 D-068（1 400 字节指整个 UDP 负载）。

**测试**（`tests/md/test_mold_codec.cpp`，13 个，先写测试、确认编译失败后再实现）：
- 按规范偏移手写的字节样本：下行包（两条消息）、心跳、会话结束、请求包；同一份样本既和编码器输出比较，也交给解码器（L3' 1d 的 `parse_packet`）解析。
- 边界：恰好装满 1 400 字节、再多 3 字节被拒；单条 1 378 字节可以、1 379 字节 `TooLarge`；65 535 / 65 536 字节；条数到 0xFFFE 后 `Full`；
  缓冲区小于 20 字节时编码器不写任何字节。
- 分包性质（固定种子 400 组随机输入，最大包长 23–1 400）：拼接 = 输入，每包 ≤ 上限，序号从起始值连续，除最后一包外每包都是因为下一条放不下才结束（贪心）。
- 逐字节截断（下行包、心跳、请求包）与多余字节；条数为 0 的请求。
- fuzz（固定种子 20 000 个输入，一半是有效包翻转几位或截断，一半是随机字节）：解析器不崩溃（ASan/UBSan 预设下越界即失败）；
  解析为 `Ok` 的输入用编码器重新编码后与原字节完全相同（编码器与解码器互逆）；请求包同样检查；另有 2 000 组请求包往返。

**负对照**（每次只改坏 `mold.hpp` 一处，gcc-debug 运行 `MoldCodec.*`，之后恢复；脚本逻辑：备份 → `sed` 改坏 → 构建运行 → 恢复）：

| 改坏的地方 | 失败的测试 |
|---|---|
| 包头条数写成 count + 1 | 7 个（手写样本、装满、条数上限、分包性质、前缀、截断、fuzz） |
| 放得下的判断 `>` 改成 `>=`（差一字节） | 装满、放不下、分包性质、fuzz |
| 去掉 0xFFFE 条数上限 | 条数上限 |
| `finish()` 后序号不前进 | 装满、分包性质、前缀 |
| 失败时不发出已拼好的前缀 | 前缀 |
| 消息长度字段写成 len + 1 | 7 个 |
| 请求包不检查多余字节 | 请求截断、fuzz |
| 条数为 0 的请求当作有效 | 请求截断 |
| 心跳编码允许 19 字节缓冲区 | 小缓冲区 |

9 个全部被抓到；恢复后 13/13 通过。

**验证**（作者本机 WSL2，2026-11-20）：六个预设 + clang-tsan 按 `scripts/check.sh` 运行，gcc-tsan 用 `setarch x86_64 -R scripts/check.sh gcc-tsan`
